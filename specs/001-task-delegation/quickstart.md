# Quickstart Validation Guide

**Status**: Design guide. Commands below are the required implementation interface;
the application, Compose files and scripts are not generated by `/speckit-plan`.
Run commands from the repository root after implementation.

## Prerequisites and environment

Docker daemon and Docker Compose v2 with healthy Linux-container support. Start with
16 GB available RAM/four CPU cores/80 GB disk for the complete stack and measure actual
usage. No host Java/Node installation is needed for the planned containerized commands.
Use synthetic accounts and files only.

```powershell
docker info
docker compose version
```

If either fails on Windows, inspect WSL before declaring validation blocked:

```powershell
wsl --status
wsl --list --verbose
```

For an explicitly identified installed distribution, invoke `wsl --distribution <name>
-- docker info` and `wsl --distribution <name> -- docker compose version`.
Use that same daemon/distribution for subsequent commands and run from its repository
working directory. Do not install Docker/WSL, change configuration, or start unrelated
services automatically. Record the exact failure if neither environment is usable.

## Setup and start (implementation must provide these interfaces)

```powershell
Copy-Item .env.example .env
docker compose --profile tools run --rm setup
docker compose config --quiet
docker compose up --build --wait
docker compose --profile tools run --rm demo-users
docker compose ps
curl.exe --fail http://localhost:8080/healthz
```

`setup` generates fresh local secrets and the selected Supabase asymmetric signing keys
into ignored runtime files; it must not overwrite existing credentials or volumes.
`.env.example` contains placeholders only. `demo-users` idempotently creates synthetic
creator, assignee, replacement assignee, and uninvolved accounts through user management;
it must not create task-specific enrollment. Operator supplies local demo passwords;
never print secrets in logs. Schema migrations are ordered one-shot startup dependencies.
Setup must also provision Realtime tenant JWT/JWKS settings and private-only operation,
plus receive-only own-user policies and the restricted activity helper. No custom Node
Socket.IO service is built. Never print server publisher keys or include them in web assets.

Frontend origin: `http://localhost:8080`. Frontend reverse proxy routes through Spring
Cloud Gateway; all backend application ports remain Compose-internal.
Supabase Studio and optional capture UI bind loopback only on documented separate ports.
`healthz` exposes only aggregate status; detailed health/metrics remain operator-only.
Container health must distinguish required dependencies from optional email/live delivery.

Email starts disabled. Optional capture profile:

```powershell
docker compose --profile email-capture up --build --wait
docker compose --profile tools run --rm delivery-policy email enable-capture
```

Only new eligible synthetic events enter capture. Use the same tool with
`email disable` to disable and suppress pending sends. No real-email mode in this demo.

## End-to-end scenarios

1. Sign in as creator and search the assignee by name/email. Create an undated task,
   add description/priority, comment, and a permitted file. Assignee can access all
   content; uninvolved user cannot discover it or reuse the attachment URL.
2. Set a deadline, move through In progress/Blocked with a reason, request a new date,
   approve as creator, then mark Done. Verify history, versions and pending-request
   resolution. Cancel/reopen a separate task; only creator can reopen Cancelled.
3. Keep two browser sessions open. Changes appear within 15 seconds without overwriting
   unsaved input. A notification emits a generic private Broadcast hint through the gateway;
   the badge reflects an HTTP inbox refresh, not a blind counter increment.
4. Reassign to the replacement user. They see historical descriptions/comments/files.
   The former assignee's copied download URL and new range request fail. Existing
   displayed content clears on refresh/denial; already saved files cannot be revoked.
5. Test a stale task version, repeated identical idempotency key, changed body with
   same key, interrupted upload, disallowed/oversized/mismatched file, inactive user,
   invalid token, empty search and failed dependencies. Errors must be explicit and
   there must be no partial successful history/notification effect.
6. Hide/reorder columns using keyboard controls, reload, and reset. Preferences are per
   account/list/browser and keep Title visible. Verify refresh/Back/Forward restore non-text
   filters/sort but never place free-text search/cursors in page URLs; copied URLs grant no access.
7. Type into task/deadline forms while another participant updates the task. Background reads
   must preserve dirty values/original version; field errors and form failures are visible.
   Failed/pending completion never looks saved. Cancel an obsolete search/read, load more
   pages, change filters and switch accounts; no stale results/cursors leak into the new view.
   Browser storage contains column preferences only, not task content/drafts/Query caches.
8. Test Realtime: own private topic succeeds; other-user/anonymous/inactive joins, public
   channels and client sends fail. Check token refresh/expiry/key rotation on pinned images.
   Existing subscription authorization is cached; verify Spring stops publishing to inactive
   users and every HTTP read remains authorized rather than claiming instant eviction.

## Crash, persistence and delivery

```powershell
docker compose stop notifications
```

Make task changes and pass reminder boundaries using the test clock in automated tests.
Task API remains usable and history/outbox persist. Then:

```powershell
docker compose start notifications
docker compose stop realtime
```

Within five minutes of worker recovery, applicable inbox work catches up without
duplicates; obsolete due-soon work does not appear alongside a now-overdue reminder.
With realtime stopped, inbox polling still works. Restart realtime and confirm reconnect
reloads the inbox even if hints were missed.

```powershell
docker compose start realtime
docker compose down
docker compose up --wait
```

Users/tasks/history/files/read states persist after ordinary recreation. Do not use
`down --volumes` or delete storage to run these checks. Any reset requires separate,
explicit authorization.

## Automated validation interfaces (provided during implementation)

```powershell
docker compose --profile test run --rm test-unit
docker compose --profile test run --rm test-contract
docker compose --profile test run --rm test-e2e
docker compose --profile test run --rm test-performance
docker compose --profile security run --rm scan-secrets
docker compose --profile security run --rm scan-source
docker compose --profile security run --rm scan-dependencies
docker compose --profile security run --rm scan-images
```

Unit command includes Java/TypeScript type/build checks; contract tests exercise real
PostgreSQL transactions and all HTTP/event definitions. E2E uses Chromium/Firefox and
keyboard workflows; performance seeds the SC-005 load and checks actual p95 thresholds.
Use controllable clocks for SC-004's 100 cases; include worker kill/restart at transaction
boundaries and SMTP-ambiguity tests. Match required outcomes in spec SC-001..SC-016,
not merely HTTP success.

Every Java service runs applicable JUnit unit/integration suites and regression cases;
test failures block the build, skipped/unavailable required suites are incomplete validation.
Sequence tests use real PostgreSQL: concurrent inserts, rollback gaps, generated-key
retrieval, owned sequence permissions, foreign/event references and restart persistence.
Contract/TypeScript/Broadcast tests round-trip decimal-string IDs above 2^53-1 without
Number conversion, reject malformed/overflow IDs and deny guessed neighboring task IDs.
Supabase account IDs remain UUIDs. Do not reset ordinary demo sequences to require
contiguous fixture IDs.
Here `realtime` in stop/start scenarios refers to the pinned Supabase Realtime Compose
service, not a custom Node process. HTTP inbox access must remain usable while it is stopped.

Image scans cover all runtime images, including upstream Supabase and gateway images;
dependency scans cover Maven/npm plus transitive dependencies. Record tool versions,
image digests, source revision, failures and exceptions. Unavailable scanners are incomplete.
High/Critical findings require remediation or a documented maintainer-approved,
time-limited exception. No vulnerability-free claim follows from this design document.
