# Data Model: Private Task Delegation

## Ownership and conventions

Application-owned row IDs use PostgreSQL `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`
with a separate owned, non-cycling sequence per table. This applies to Task, Comment,
Attachment, DeadlineRequest, ActivityEvent, TaskOutbox (`event_id`), Notification and
DeliveryWork. Foreign/reference IDs use the same bigint type as their source; source event
references are copied, not regenerated by consumers. Tables with documented composite or
natural keys (MutationReceipt, ReminderIdentity, ConsumedEvent, DeliveryPolicy) retain
those keys without unnecessary surrogate IDs.

Supabase Auth user IDs and all user references remain UUIDs, including creator, assignee,
author, actor, requester, resolver and recipient IDs. Client-generated idempotency/upload
operation keys remain UUIDs; lease claim tokens remain unpredictable random tokens, not
sequence values. They are retry/fencing tokens, not application entity primary keys.
Broadcast signal IDs reuse their durable DeliveryWork ID rather than generating a UUID.
Do not modify Supabase-managed Auth/Storage identifiers.

Sequences are not gapless, commit-order clocks, or authorization tokens. Rollbacks,
conflicts and concurrent inserts may leave gaps or commit out of allocation order; never
use `max(id)+1`, reset sequences during ordinary startup, or reuse deleted IDs.
Use insert `RETURNING`/JDBC generated keys rather than a separate sequence lookup.
Grant runtime roles only required owned-table/sequence privileges, never cross-service
sequence administration. Privileged import/restore must synchronize sequence state
before writes resume.

Java represents entity IDs as `Long`; JSON/Broadcast and URL IDs use canonical positive
decimal strings in the range 1..9223372036854775807. TypeScript treats IDs as opaque
strings and MUST NOT convert them to Number. Bigint versions/epochs follow the same
string serialization rule; small bounded counts and schema versions remain JSON numbers.

Use `timestamptz` instants; IANA time-zone names; server-generated audit times;
SQL constraints plus service validation. Runtime roles are not owners/superusers and cannot
bypass schema restrictions. Migration roles are separate. Application schemas are excluded
from Supabase's exposed REST schemas and receive no anon/authenticated grants.
Do not mutate Supabase-managed tables except through supported identity integration.

Stable user UUID references and task bigint references preserve history after deactivation;
identity deletion is soft in the projection while referenced. A shared physical PostgreSQL
instance is not permission to join/mutate another service's business tables.

## Schema and migration ownership

| Schema | Owner role (migrations) | Runtime role | Migrated by |
|--------|-------------------------|--------------|-------------|
| `identity` | `identity_owner` | none (read-only contract grants to task/notification runtime roles) | `db-bootstrap` job |
| `task` | `task_owner` | `task_app` | `task-api-migrate` job |
| `notification` | `notification_owner` | `notification_app` | `notifications-migrate` job |
| Realtime policies on `realtime.messages` | Supabase administrator | n/a | `db-bootstrap` job |

Roles, schemas, default privileges and cross-schema grants are created only by the
privileged bootstrap job. Each service has its own Flyway history table in its own schema.
Versions are per service and assigned at merge time; see plan.md.

## Identity-owned directory

**DirectoryUser**: `user_id` (Auth stable UUID, unique), `display_name` (1..200, defaults to
the email local part), `email`, `active`, `time_zone` (IANA name present in
`pg_timezone_names`, default `DEFAULT_TIME_ZONE`), `deleted` (soft-delete flag), `updated_at`.
User management maintains it automatically through identity-owned `auth.users` triggers in
the same transaction, covering creation, activation/deactivation and profile changes. `active` is
false when the Auth user is banned, deleted or unconfirmed; only server-controlled Auth fields
affect it. `display_name` and `time_zone` come from user-editable metadata; an invalid
zone keeps the previous value. The `tools/identity reconcile` command repairs drift. Read-only views/operations expose
only necessary directory fields to task/notification services. No task-specific enrollment.
Names/email are not ownership keys; activation cannot derive from user-editable metadata.
Identity-owned Realtime authorization helper checks only the verified `auth.uid()` activity
against this directory. It exposes no rows and grants no task-table access. Policies on
Realtime's managed messages table allow own-topic Broadcast receiving only; those
authorization probes are not persisted application inbox data.

## Task-owned schema

**Task**: `id`, immutable `creator_id`, `assignee_id`, `title` (trimmed 1..200 characters),
`description` (0..20,000 characters), `priority` (`low|normal|high`),
`status` (`todo|in_progress|blocked|done|cancelled`), nullable `due_at` and
`due_time_zone` (both present or both absent), nullable `blocked_reason`/
`cancellation_reason` (1..2,000 when applicable), `created_at`, `updated_at`,
nullable `completed_at`, monotonically increasing `version`.

Creator/assignee must be active when assigned. Open = todo/in_progress/blocked.
Only blocked has a current blocked reason; only cancelled has a cancellation reason;
only done has a completion time. Title/description/priority/assignee/deadline edits are
creator-only. Date-only deadlines resolve to 23:59 in the creator's selected zone;
explicit ambiguous/nonexistent local times require a specific offset or corrected input.
Filter dates use the viewer's selected zone and inclusive calendar dates translated to
a half-open instant range. Database stores instants, never ambiguous local timestamps.

Indexes cover creator/assignee with deadline/status, plus stable `(created_at,id)` tie breaks.
Case-insensitive title/description substring search may use `pg_trgm` indexes after measuring.
Sort null deadlines last in either direction. Cancelled remains discoverable to participants.

**Comment**: `id`, `task_id`, `author_id`, `text` (trimmed nonempty, <=10,000 characters),
`created_at`; append-only. Current participants may add even when Done/Cancelled.
Stable chronological order is `(created_at,id)`.

**Attachment**: `id`, `task_id`, `uploader_id`, sanitized display `original_filename`,
`content_type`, `size_bytes` (1..10,000,000), opaque `object_key`, `checksum`,
`state` (`staging|ready|failed`), `created_at`, nullable `finalized_at`, `upload_operation_id`.
Private object keys never appear in public responses. Actual format must be allowed and
match supplied extension/type; TXT must pass text validation. DOCX/XLSX ZIP structures
receive bounded parsing, not extension-only acceptance. Only ready records are visible.
Finalization commits ready metadata, history and outbox together after authorization.
Failed staging is operational state, not a successful user-visible attachment.

**DeadlineRequest**: `id`, `task_id`, `requester_id`, `proposed_due_at`,
`proposed_time_zone`, `reason`, `state` (`pending|approved|declined|withdrawn|superseded`),
`created_at`, nullable `resolved_at`, `resolved_by`, `resolution_cause`, `version`.
Unique partial index on task where state=pending. Only a distinct assignee of an open task
may submit; creator decides; requester withdraws. Proposal must differ from the current
deadline, or supply a date to an undated task. Removal requests are not supported.
Direct date changes/removal, reassignment, Done, and Cancelled supersede pending requests.
Decision and task change lock the same task first to serialize races.

**ActivityEvent**: `id`, `task_id`, `actor_id` (or explicit system actor for operational
events), `type`, `occurred_at`, `changes` (allowlisted previous/new values), optional
`comment_id`, `attachment_id`, `deadline_request_id`. User-visible business events are
immutable; retain earlier descriptions, assignments, blocked/cancellation reasons and
request decisions. Current participants see all history regardless of assignment date.
Never include tokens, storage credentials, or internal stack traces.

**MutationReceipt**: unique `(actor_id,operation,idempotency_key)`, request hash,
response status/body/reference, creation/expiry time. Store with the mutation commit.
Keys retained at least seven days; clients retry only within that window. Validate current
access before returning cached responses. Same key/different body is a conflict.
An upload receipt links to a stable attachment operation and staging object.

**TaskOutbox**: `event_id`, `task_id`, `event_type`, `schema_version`, `actor_id`,
minimal recipient candidates, nullable reminder identity, `created_at`, `available_at`,
`state` (`pending|leased|acknowledged|failed`), `claim_token`, `lease_until`,
`attempt_count`, sanitized `last_error`. Do not copy private comments/descriptions.
Task API alone claims/acks via its internal contract; notification SQL role has no access.
Unique event identity; persistent claims expire for recovery.

**ReminderIdentity**: unique `(task_id,recipient_id,reminder_type,due_at)`,
`event_id`, nullable processed time. Due-soon and overdue are different types. Insert
identity and outbox atomically under the task lock. Do not delete identities on reschedule,
removal, reassignment or reopening; restoring a deadline must not duplicate a reminder.
Current-state checks suppress an obsolete pending event. An acknowledged applicable
delivery is not generated again. A new assignee has a distinct recipient identity.
Suppression is not delivery: if reopening, reassignment, or restoring the same deadline
makes a previously suppressed reminder applicable again, the task-owned evaluator may
requeue that identity with a new event ID only when no inbox delivery was committed.
Source acknowledgment distinguishes delivered from suppressed; a consumed suppressed
event must not permanently prevent the still-undelivered reminder from becoming eligible.

## Notification-owned schema

**ConsumedEvent**: unique source `event_id`, payload hash, processing time.
Same identity/different payload fails visibly; insertion deduplicates crash redelivery.
Retain per-recipient delivered/suppressed outcomes for replaying source acknowledgments.

**Notification**: `id`, `source_event_id`, `recipient_id`, `task_id`, generic `type`,
`created_at`, nullable `read_at`. Unique `(source_event_id,recipient_id)`.
Body contains no private task text. Reads/counts require recipient identity and current
task access, not an old recipient snapshot. Reassignment never exposes another inbox.

**DeliveryWork**: `id`, `notification_id`, `channel` (`realtime_hint|email`),
`event_idempotency_key`, `state` (`pending|leased|sent|failed|suppressed|unknown`),
`available_at`, `lease_until`, `claim_token`, `attempt_count`, sanitized error,
nullable provider receipt, `policy_epoch`, `created_at`, `sent_at`.
Unique `(notification_id,channel)`. Broadcast sends may retry with duplicate harmless hints.
Email adapter uses its stable idempotency key; SMTP ambiguity is unknown and requires
investigation rather than automatic resend.

**DeliveryPolicy**: fixed channel key, `enabled`, monotonic `epoch`, `updated_at`.
Default email disabled. On disable, advance epoch and suppress outstanding email work;
events occurring while disabled produce no sendable backlog. On enable, start another
epoch and accept new events only. Task events carry source time; do not treat worker
processing time as event creation when applying enablement. Persist policy history
intervals so catch-up can evaluate the source event's enablement window.

## Browser-only view preferences

Versioned column preferences contain visibility/order for allowlisted column IDs, scoped
by verified user UUID and list type in this browser. Title stays visible; invalid records
reset with a notice. No database entity, cross-device sync, task rows, tokens or drafts.
Validated non-text filters/sort belong in the Router URL; free-text search/cursors remain
in memory. Query keys include user, view and normalized query conditions, with page cursors
preserved losslessly. Form dirty values and server versions remain in memory only.

## State and transaction rules

| Action | Allowed actor | State effect |
|--------|---------------|--------------|
| Start/stop progress | Current participant on open task | todo/in_progress; clear blocked reason when leaving blocked |
| Block | Current participant on open task | blocked with reason; deadline/reminders remain effective |
| Complete | Current participant on open task | done with completion time; pending request superseded |
| Reopen Done | Either participant | todo, clear completion; confirm past deadline |
| Cancel | Creator on open task | cancelled with reason; request superseded; reminders suppressed |
| Reopen Cancelled | Creator only | todo; clear cancellation reason; confirm past deadline |
| Approve request | Creator, request pending/task open | Apply proposed deadline, record decision, schedule evaluation |

No direct done-to-blocked or cancelled-to-done. Reopen first. Mutations check expected
version after locking; stale data returns conflict without partial history or outbox.
Comment/file additions do not overwrite task fields or force a dirty edit to lose text.
Lock task consistently before child decision/scheduling operations; bounded retry on
database deadlock, with explicit failure if exhausted.

Notification consumption is a separate local transaction: deduplication + inbox entries +
delivery work, then source acknowledgment. No transaction spans PostgreSQL and HTTP/SMTP.
Check recipient activity/current task authorization before persisting/dispatching and when
serving the inbox. Already delivered/downloaded content cannot be remotely erased.
